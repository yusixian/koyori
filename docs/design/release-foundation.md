# 文档站、发布与开源基线

> 2026-09-22；用户确认：自用优先、从首版开源、文档站与分发同步建设、验收后可直接发布。工程起点正在按下文建设；实际验证与发布状态见实施状态，不能把流程要求当完成证据。

## 现状与范围

本文起草时项目仅有文档与品牌资产；当前工程能力和验收结果以 [实施状态](../implementation-status.md) 为准。brand/README.md 确认正式 Logo。旧路线图把分发排在 MVP 后，与本次要求冲突，以本文的新顺序为准。

目标：第一个可用版本即可从公开文档站找到说明、版本记录和安装包；开发代理能按明确证据完成检查、准备发布，并在授权的流水线中发布。

Non-Goals：本次不生成空壳 CI、不发布不存在的安装包、不建设账户/支付、插件市场、多平台全矩阵或通用云服务。已确认参考 cos-tool-bot 的文档站与 v0.3.0 更新说明；本地核对依据和适配边界见 [参考实践](cos-tool-bot-reference.md)。

## 方案与取舍

| 方案 | 优点 | 代价 | 选择 |
| --- | --- | --- | --- |
| 同仓文档站 + GitHub Releases 分发 | 文档与功能一起审查，首版发布设施较少 | GitHub 下载可用性受网络影响，需协调站点和渠道更新 | 起步推荐，实际部署待确认 |
| 同仓站点 + 对象存储/CDN 分发 | 下载域名及缓存策略可控 | 多一套上传、权限和完整性维护 | 下载需求明确后追加 |
| 后期再补文档与发布 | 原型阶段省事 | 容易长期停留在源码运行，无法验证安装升级 | 不采用 |

用户已确认 Dokploy 为部署平台：站点在同仓 apps/site 独立构建，作为 Dokploy 应用部署；桌面安装包仍在 macOS 构建环境产出，应用发行物不放站点镜像。站点框架、打包器与 updater 在首个工程切片中配套选择，优先验证参考项目的 Fumadocs + React Router 预渲染方案；依赖版本与桌面打包器仍须在初始化时验证，不照搬参考项目锁文件。

## 文档站的首版内容

- 首页：定位、真实截图、当前成熟度和平台支持。
- `/docs`：安装、首次使用、服务接入、Skills 管理、权限与数据位置、导出恢复、排障；只有实现且验证的功能才进入正式使用指南。
- `/download`：明确版本、preview/stable、平台/架构、最低系统要求、签名状态、安装说明、校验值及历史版本入口。没有安装包时不显示假的下载按钮。
- `/changelog`：每版功能、修复、已知限制、迁移和升级提示；链接到对应 Release 与版本适用文档。
- 贡献与安全入口：开发设置、检查命令、报告问题、私密漏洞报告方式、代码许可证与品牌说明。

开发文档标为 unreleased；公开默认文档对应最新已发布版本。初期不复制每个 patch 的整站文档，但破坏性变化保留版本适用说明及必要的历史指引。下载页与应用读取同一发布清单，避免手写多个“最新版”。

公开站点内容使用显式内容目录，不自动发布仓库根 docs 全部内容；发布正文是明确纳入的例外。内部设计留在源码仓库意味着开源后同样可被读取，仍须脱敏，不能把“不生成站点页面”误当作保密。文档可无数据库、无 Bot Token、无生产凭据独立开发。验收匿名访问、深链刷新、搜索、移动导航、真实 404 和历史版本页。

## Dokploy 部署约定

站点构建通过后，部署已验收的 commit 或不可变镜像，并核对实际部署版本。预览环境与正式域名分开；生产部署凭据只在受保护环境提供。站点不需要持有用户 Bot、MCP 或其他服务的管理密钥。域名、TLS、健康检查和失败回滚在首次上线时验收。

站点文档与应用更新渠道独立发布；应用发布产物可下载后才推广新版下载入口。Dokploy 回滚站点只能回滚页面，不能撤回已安装应用或回退用户数据库。用户现有服务继续在各自 Dokploy 应用中运行，接入 Koyori 不要求迁移服务或数据库。

## 版本与更新说明

初始化工程时建立唯一产品版本源；建议首个候选 `0.1.0-alpha.1`，仅为命名示例，当前没有该版本。Git tag 使用 `v` 前缀；正式、预发布版本按 SemVer 排序，不用字符串或提交日期比较。

0.x 阶段约定：patch 为兼容修复，minor 为新能力或明确说明的不兼容变化；alpha/beta/rc 用于候选迭代。内部不发布的包无需各自独立发版。站点单独修正文案不强迫应用升版；面向用户的 CLI 随应用版本统一。

沿用参考项目的 `docs/releases/vX.Y.Z.md` 作为每版发布说明唯一正文；未发布草稿放 `docs/releases/unreleased.md`，归档后由构建脚本生成站点版本页，并作为 GitHub Release 的 notes 输入。生成页面不手工修改或重复提交；版本索引自动生成或检查完整性。自动收集 commits/PR 只是草稿，必须剔除内部细节、个人信息与未交付声明。

发布清单包含版本、渠道、commit、平台/架构、最低系统版本、下载地址、SHA-256、签名/公证状态、说明链接。updater 所需专用元数据由选定打包工具生成，并与清单核对，不先发明自定义 updater 协议。

## 从验收到发布

1. 合并前：相关检查、行为测试、依赖/secret 检查及文档构建；所需 CI 状态必须通过。
2. 维护者授权的发布入口选择不可变 commit 和目标版本，检查唯一性、变更说明与工作树状态。
3. 在可信隔离环境构建候选，完成所需签名/公证，记录产物摘要；签名完成后的文件才是验收对象。
4. 验收实际安装包：干净安装、启动、核心流程、权限、版本显示、退出重开；已有版本时从上一公开版本升级并验证数据保留。更新通道在测试源验证失败、中断和重试。
5. 发布门禁核对同一 commit、版本和产物摘要的验收记录。人工步骤可由维护者留证，自动步骤由 CI 留证；没有配置必需检查时不能把“无检查”当通过。
6. 上传通过验收的原始产物，核验远端文件和摘要后公开 Release，最后更新渠道与站点入口。发布任务重试不覆盖不同字节的同版本文件。
7. 验证公网下载、Release 版本、站点说明与更新源一致，记录结果。站点发布失败时保留可用 Release，重试站点，不重复发版。

同渠道发布串行执行。验收后不重新构建；任何产物变化重新验收。stable 用户不自动收到 preview。自动重启不得中断配置写入或其他尚未安全停止的任务。

“验收后直接发版”落实为维护者配置一次受保护的发布入口/环境策略；以后在授权范围内连续执行。不是让任何 PR、网页内容或 AI 自评触发带凭据的发布。首版尚无上一版本时记录升级检查不适用；后续首次提供 updater 前必须验证真实升级路径。

## 安全与开放边界

公开前选定开源许可证并加入 LICENSE；品牌与历史图片的许可范围单独说明，第三方依赖与借用素材保留声明。本轮起步选用 MIT，品牌与第三方说明单列；参见根 LICENSE。

检查拟公开 Git 历史、站点源、附件、样例和发行包；不发布真实会话、服务器连接信息、个人路径、密钥或数据库。泄漏凭据需要撤销/轮换，不能仅靠删除当前文件或加忽略规则。公开历史重写另行评估与授权。

公共 PR 在无 secrets 的隔离环境执行；可信发布与 PR 验证分开。禁止把不可信代码送进有个人资料/生产凭据的持久 runner；限制 token 权限，固定第三方 Action 完整 commit SHA。初始化工程时建立 secret 扫描及依赖漏洞/许可证检查；高风险发现需要有依据的处置，例外记录理由、责任人与复查期限，不用永久忽略消除告警。

远程 GUI 作为独立不可信内容隔离，不获得工作台本地权限。连接凭据与会话按服务隔离，新增权限显式授权。具体实现还需验证 OAuth 回调、撤销、外部导航与 IPC 边界。

发布前加入 SECURITY.md，提供实际可用的私密报告方式；不把尚未启用的 GitHub 私密报告功能写成可用。安装包摘要校验用于检测损坏，不能代替代码签名或来源认证。

## 失败与回滚

- 检查、签名、公证或安装验收失败：停止推广，不修改稳定渠道。
- 坏版本已发布：撤回推荐、停止更新分发并标注问题，发布新版本修复，不移动旧 tag 或替换同版本产物。
- 数据迁移：升级前保护持久数据，验证备份恢复；回退应用不等于回退数据库。无法兼容时保持数据并说明恢复步骤。
- 无签名条件：只允许明确标识的手动安装 preview，不承诺正式自动更新体验；签名/公证准备好后再开放对应能力。
