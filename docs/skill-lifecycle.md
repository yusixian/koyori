# Skills 使用统计与整理建议

> 2026-09-09 的产品候选，2026-09-22 补充状态：Claude Code 本机账本、30/90 天统计、规则与复查偏好已进入实现；准确范围见 [当前实现](design/usage-ledger.md) 和 [验收状态](implementation-status.md)。本文其余长期候选不代表已经交付，也不授权清理现有文件或安装 hooks。

当前首版以 [扩大版 0.1 草案](design/mvp-0.1.0.md) 审阅：提议将可恢复整理和按需 Agent 解释前移，下面长期分期不再表示 AI 一定等到 0.1 之后。计数真实性、隐私和授权原则不变。

## 想解决的问题

用户需要知道哪些 Skill 经常使用、哪些长期没有观察到调用，以及整理后会影响什么。目标是持续生成有证据、可审阅的整理报告，帮助保留常用能力、减少无关可见资源，并找回暂时收起的能力。

报告按客户端、Profile、项目和时间窗口展示；支持近 7/30/90 天与自定义区间。除 Skills 外，识别同源 commands 和 plugin 提供的资源，但不能用 Skill 调用量代替整个 plugin 的使用量。

## 三个互补方向

| 方向 | 提供的价值 | 取舍与顺序 |
| --- | --- | --- |
| 本地使用账本 | 调用次数、涉及会话、最近使用、来源与证据覆盖 | 最先做；即使没有 AI 也有用，但历史记录可能不完整 |
| 规则整理助手 | 定期检查闲置、复查日期、重复候选，解释触发条件 | 随自用 MVP 做；阈值透明可调整，默认只建议 |
| AI 资源顾问 | 结合项目需求、内容和引用关系，建议保留、合并、缩小作用域或更新 | 后续增强；必须引用账本证据，不能生成调用数字 |

推荐按这个顺序渐进完成。第一条只读流程可以是：选择资源根和历史范围 → 扫描 Skills → 导入可识别的使用事件 → 展示排行和数据缺口 → 生成首份规则报告。

## 什么算一次使用

至少分开记录以下证据，不混成一个精确数字：

- **明确调用**：客户端可识别的 Skill 调用事件；调用尝试、失败、被阻止与已加载分别标记。调用事件不证明任务成功或 Skill 有效。
- **显式请求**：用户通过命令或结构化输入选择 Skill；没有后续加载证据时，仅算请求。
- **读取线索**：工具读取 SKILL.md，可能是执行准备，也可能只是审查或编辑。单列为“疑似使用”，不能直接加入明确调用次数。
- **仅提及或可见**：出现在对话、资源列表、描述注入中，不算调用。被其他 Skill 引用是保留依据，不自动折算一次调用。

默认展示明确调用次数和去重会话数，同时允许展开请求、失败和疑似使用。一个会话多次调用可以计多次；同一次请求在 hook、工具结果和日志中出现只计一次。关联证据更新状态，不额外加数；无法可靠关联时标记待归因。

导入应处理重复文件、恢复/分叉复制的历史、子代理会话、截断或损坏记录。用来源、原始事件身份和会话关系去重，不能仅按文本或时间去重。历史别名、command 转发和 plugin 命名空间保留调用入口与最终来源，不凭同名合并。

每条统计必须附带：请求窗口、实际可读取范围、覆盖的客户端/Profile/项目、解析失败与缺口、采集器版本、最近同步时间。覆盖日期只是有记录的范围，不保证期间无缺失。新发现日期不冒充安装日期；当前安装状态不冒充过去的可见状态。

界面区分“覆盖范围内明确调用 0 次”“覆盖不足”“无法识别调用”。不能把没有日志、未支持版本、未登记 Profile 或离线设备都显示为 0；跨客户端汇总同时保留各自口径，不宣称完整总量。

## 从哪里取得证据

优先使用客户端原生只读接口或本地会话记录，由适配器归一化；模型负责解释，不负责数日志。这里的 Claude Code / Codex 本地数据入口与云模型 API 是两件事，不能假设登录模型账户就能读取本机所有历史。

| 来源 | 候选接入方式 | 验证边界 |
| --- | --- | --- |
| Claude Code 历史 | 用户选定配置根内的本地会话记录，识别结构化 Skill 工具事件和命令展开证据 | 日志字段、保留期、子代理及直接命令路径按版本验证；不把简单名字搜索当调用统计 |
| Claude Code 后续增量 | 经用户选择安装最小本地 hook，记录调用元数据；日志补扫 | 官方文档区分 Skill 工具路径与直接命令展开路径；只监听 PreToolUse 会漏掉后者。实际事件支持需探测 |
| Codex | App Server 的 skills/list 做资源盘点，thread/list、thread/read 查询可访问历史；必要时适配所选本地记录 | 资源列表不是次数接口；结构化 skill 输入是显式请求线索，历史是否保留及自动调用如何归因需实测 |
| Koyori 自己发起的操作 | 记录选择、请求和返回状态，与客户端事件关联 | 只能覆盖 Koyori 经手的行为，不能冒充外部会话总量 |
| 云端或其他宿主历史 | 未来在有明确授权和可用导出/API 时接入 | 当前不承诺跨设备云端总表；ACP 会话接入不自动提供旧历史 |

2026-09-09 核对依据：[Claude Code hooks](https://code.claude.com/docs/en/hooks) 说明 transcript_path、工具生命周期和 UserPromptExpansion；[OpenAI Docs：Codex App Server](https://learn.chatgpt.com/docs/app-server) 说明资源列表、会话读取及结构化 Skill 输入。本机 CLI 确认为 0.153.4，help 暴露 app-server 与 schema 生成入口；本次未读取个人会话、运行历史接口或安装 hook。当前没有验证统一的每 Skill 累计次数接口。

实现前用隔离样本验证：手动调用、模型主动调用、失败/被阻止、单纯读文档、重复导入、子代理和分叉历史。无法可靠归因的路径保持未知，不用 AI 补成事实。

## 机械规则候选

下面阈值是可配置的起点，不是自动删除条件。规则仅在用户启用相应检查后定期运行。

| 规则 | 示例条件 | 建议 |
| --- | --- | --- |
| 长期闲置 | 可评估的观察期达到 90 天，未观察到明确调用；新资源先给 30 天观察期 | 检查是否改为项目可见或归档 |
| 低频且局部使用 | 90 天内仅 1–2 次，且仅在某个项目出现 | 从全局缩小到该项目；其他 Profile 覆盖不足时提示 |
| 到期复查 | 用户设置的复查日期已到，或上次人工核验超过指定天数 | 提醒检查适用性和内容，而非判断已失效 |
| 重复候选 | 内容指纹相同、旧名转发，或已安装 plugin 存在近似能力 | 对比版本、调用入口、依赖、修改和真实可用性后再选择保留来源 |
| 内容可能过时 | 检测到版本约束冲突、失效引用或有可靠依据的上游替代 | 提议修复或升级；不能只凭文件 mtime 宣称过期 |

保护条件先于闲置建议：用户标记“始终保留”、新安装观察期、已知被引用资源、应急/发布用途、用户指定的未来项目需求。静态引用扫描是线索，未发现引用不代表无依赖。插件也可能提供 hooks、MCP、LSP 或其他能力，Skill 零调用不足以建议卸载整个插件。

日历时间之外，可展示“相关项目活跃期间仍未使用”的信号：项目休眠三个月与项目每天使用但 Skill 始终未触发，应有不同解释。活跃度及可见性没有可靠记录时不计算使用率，也不估算精确上下文或 token 节省。

## AI 能补什么

AI 读取用户选定的资源内容、统计摘要、依赖线索和项目背景，提出几种可能解释：能力已被替代、触发描述不清、作用域不合适、项目暂时休眠，或未来任务仍需要。低频资源也可能值得改进触发描述，而不是收起。

建议卡包含：资源及来源、统计窗口和证据、规则命中条件、AI 判断及反证、影响的项目/Profile/引用方、建议动作、可恢复性与未决问题。重复建议展示具体差异；“同名”“功能相似”均不等于等价替代。

提供“保留”“稍后提醒”“只在指定项目启用”“归档”“查看整理计划”。用户拒绝建议时可记录原因，供后续规则和 AI 参考；证据不变时不反复推送。先做规则筛选，AI 按需分析少量候选；后台 AI 单独开关，并可限制频率和费用。

## 自动提醒与整理闭环

默认候选节奏为每周摘要，支持手动检查；应用/托盘运行时调度，退出后下次启动补一次检查，不补发每个错过的提醒。新增调用、资源修改或依赖变化会使旧建议失效，应用前重新扫描并核对版本。

“过期”分成闲置、复查到期、内容失效三个状态。复查日期默认保存在 Koyori 元数据中，不擅自修改 SKILL.md；不要求用户维护新的 frontmatter 标准。

优先保留原件、撤销受管部署、缩小可见范围或归档。归档应保留完整资源目录与来源/部署关系，并放在已验证不会被客户端扫描的位置；共享源或全局残留要明确说明。先预览计划与影响，再经授权执行，提供恢复；文件冲突遵守既有 revision 检查。未来自动规则最多从用户授权的可恢复动作试起，永久删除始终单独确认。

## 数据与隐私

用户选择要读的客户端/Profile、项目和历史范围。采集默认留在本机，只保存统计所需事件元数据、证据定位和覆盖记录，不复制会话原文或凭据。云模型调用前显示将发送的摘要或选定片段并脱敏；本地 ACP 不代表模型推理离线。

规则、保留偏好、人工判断和建议处置记录属于持久数据。原日志可重读时统计索引可以重建；若希望在日志轮转后保留历史用量，需明确选择持久保存最小事件账本及保留期，不能把唯一证据当缓存清除。原始证据已不存在时标记“仅保留采集记录”，不承诺仍可打开原文。

GUI 与 CLI 共用统计和规则能力；以后 Claude/Codex 可通过 Koyori 的只读能力查询“近 90 天排行”“闲置候选及原因”。CLI/AI 查询统计不等于批准整理。MVP 先做本地查询与可读/结构化报告，是否追加 MCP 查询入口按实际需求决定。

## 分期与待验证问题

1. 第一阶段加入资源清单、一个客户端的历史导入和使用账本，确认计数口径，再扩展另一客户端；不要求先支持全部日志版本。
2. 自用 MVP 加入规则报告、保留/稍后提醒、每周摘要；整理执行复用已有计划、恢复与部署能力。
3. AI 阶段加入内容对比、依赖和项目背景分析；后续再探索已授权的受限自动整理。

仍需通过样本决定：各客户端能准确识别哪些事件；是否值得安装增量 hook；历史保留多久；默认阈值是否符合实际节奏。先验证“看得懂次数及缺口，能判断为何建议收起”，再扩充分析功能。
